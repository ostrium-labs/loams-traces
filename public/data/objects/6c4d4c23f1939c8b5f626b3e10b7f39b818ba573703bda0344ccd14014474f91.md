# BQ1: benchmark every Loams engine toward 1B QPS (coordinator brief)

Owner, 2026-10-28: "task it to benchmark all loams engines for 1B QPS".

## What 1B QPS means here (honest framing, applies to every lane)
- 1B QPS is a fleet-level target. This laptop has 14 cores and 15 GB RAM, and the cloud accounts are broken (AWS SCP deny, Azure tenant, empty GCP SA). Nobody measures 1B QPS here, and no doc may claim it was measured.
- Each lane produces three things:
  1. **Measured:** single-node peak QPS and latency (p50, p99, p99.9) for the engine's hot path, on pinned cores, with a fixed core budget (`taskset`, server and load generator on disjoint cores, usually 6+6).
  2. **Scaling:** measured throughput at 1, 2 and 4 shards, nodes or partitions locally (where the engine shards), giving a scaling-efficiency number.
  3. **Projected:** the nodes and cores needed for 1B QPS, computed from (1) and (2), with every assumption written down. Label it "projected, not measured". Name the bottleneck that breaks linear scaling (PD/TSO, metadata, coordinator, network) and what would fix it.
- Also profile the hot path (`perf` or `cargo flamegraph` if present, otherwise `tokio-console` or counters). File concrete fixes as issues, and make the cheap ones as PRs with before/after numbers. Higher per-core QPS is the real lever toward 1B.

## Rules
- AGENT-RULES.md applies. The no-build rule of 2026-10-27 does NOT apply to BQ1: build release binaries with `.he0-shared/buildslot.sh cargo build --release -j 4 ...`.
- **Run every measurement under the exclusive bench lock:** `.he0-shared/benchslot.sh <lane> <cmd>`. Keep each hold to 15 minutes or less. Write harness code while you wait. Numbers taken outside the lock are invalid.
- Disk is tight: /home has about 18 GB free and /mnt/Projects about 25 GB. Delete your own datasets after each run and keep results JSON small. Use no `/tmp` for data; use your worktree or /mnt/Projects/bench-data/<lane>.
- No cloud resources. Confluent belongs to lane CFB only.
- Kill only the processes you started, by PID.
- Code goes in `bench/<engine>/` (harness scripts, plus a load generator if no standard tool fits). Results go in `bench/results/bq1/<engine>/*.json`. The report goes in `docs/benchmarks/2026-10-28-1b-qps/<engine>.md`. One PR per engine, base `dev`. Status goes in `.he0-shared/bq1-<engine>-status.md`.
- Prefer standard tools when present: oha (HTTP), pgbench (PG wire), memtier/valkey-benchmark (RESP), kafka-producer-perf-test or rdkafka perf (Kafka), go-ycsb. If a tool is missing, write a small Rust or Go load generator in `bench/<engine>/loadgen`; don't install system packages.
- BQ1-SUM merges all engine reports into `docs/benchmarks/2026-10-28-1b-qps/README.md`: a table of engine, measured QPS/node, scaling efficiency, projected nodes for 1B, bottleneck and links.

## Quiet window for final numbers (added 2026-10-28 evening)
- The bench lock only keeps out other benchmarks, not builds. The gateway lane measured a load average of 9.8 with 39% iowait during a "6-core" run, so the curve was really measuring contention.
- **For the numbers that go into a report:** inside your benchslot hold, run `echo $(( $(date +%s) + 1200 )) > .he0-shared/quiet`. Wait until `pgrep -x rustc` is empty and the load average is below 2. Measure, then `rm .he0-shared/quiet`. While that file holds a future time, buildslot.sh starts no new builds. Keep the window to 20 minutes at most.
- Record the load average, iowait and the server's CPU-seconds in every result. Report efficiency per busy core alongside the raw curve.

## Pipelining everywhere (owner, 2026-10-28: "add pipelining in every point to get there")
- Every hot path must support request pipelining and batching end to end: client → gateway → engine → storage. Each lane makes sure that holds for its engine, implements it where it's missing, and measures with it.
  - **HTTP:** HTTP/1.1 pipelining plus HTTP/2 multiplexing. Many streams per connection; the gateway must not serialise a connection's requests.
  - **RESP:** pipelined commands, processed in batches per read and with batched TiKV gets/puts (batch_get, batch_put). No single round trip per command.
  - **PG wire:** the extended-protocol pipeline mode (libpq pipeline, `pgbench -M extended` with `\startpipeline`). The gateway's SNI proxy must forward without per-message flushes.
  - **CH native and HTTP:** multiple queries per connection, batched inserts.
  - **Kafka:** many in-flight requests per connection (max.in.flight > 1), larger batches with linger and compression. The gateway must handle concurrent requests on one connection; don't make it strictly serial.
  - **Temporal and Resonate:** concurrent RPCs per gRPC channel, batched store commits (group commit).
  - **Meter:** batched gate checks and batched sink appends.
  - **Graph and Git:** batched lookups and multi-ref updates.
- Inside engines, look for one fsync or one store round trip per request and replace it with group commit or batching where correctness allows. Durability semantics must not change; say what was batched.
- Report two numbers per engine: unpipelined (depth 1) and pipelined (depth N, with N stated), plus requests/s against operations/s. The 1B projection uses the pipelined number, labelled as such.

## Native APIs only, plus one combined run (owner, 2026-10-28: "native apis only … combined all three as single run")
- **Measure each engine only through its own native API.** Compatibility layers drop out of the headline numbers. They may stay in reports as a footnote, but they are not the 1B path. Native API per engine:
  - **KV:** the loams-kv / loams-hot Rust API and the TiKV client (batch_get/batch_put). Not RESP or CQL.
  - **Postgres:** PG wire to compute, which is native for Postgres. The gateway SNI path is a footnote.
  - **SQL:** MySQL wire to TiDB (native), plus raw TiKV txn/raw API throughput.
  - **House:** CH native TCP protocol.
  - **Streams:** Iggy native TCP/QUIC. Not the Kafka gateway.
  - **Durable:** the Resonate native API, and the loams-temporal-store API. The Temporal frontend gRPC is a footnote.
  - **Meter:** the native gate and sink APIs.
  - **Graph:** the Grafeo native API. **Git:** the native git-on-S3 ops.
  - **Gateway:** the Loams native API (Connect/HTTP).
  - **RisingWave, Flink, Spark:** their native ingest and SQL endpoints.
- **Combined run (lane BQ1-ALL).** One harness starts every engine and every native load generator at the same time on one machine. It splits cores per engine and reports per-engine QPS plus the total aggregate QPS from one simultaneous run. Each lane provides `bench/<engine>/native-load.sh --duration --cores --depth` that writes the common JSON line format (`{engine, op, qps, p50_ms, p99_ms, depth, cores}`) to stdout. BQ1-ALL owns `bench/all/`.
