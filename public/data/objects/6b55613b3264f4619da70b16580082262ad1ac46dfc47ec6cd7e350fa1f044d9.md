### DX1 — promise-ID grammar, run as origin (Task 6 agent, 2026-10-25)
Coordinator decision (owner may veto): replace design 74 §5.4's `wft:{ns}:…` grammar with FW7's §8.0 form
(fork lead's preferred form, `protocol-profile.md` §8.0 and §10.1), so the origin is the run, not the kind.
Exact form as implemented in `loams-temporal-resonate::ids` (follow-up to #1209):
```
origin = <ns>.<wf>.<run>                         no ':'; one origin per workflow run
wft    = <origin>:wft.<scheduled_event_id>
act    = <origin>:act.<scheduled_event_id>.<attempt>
tmr    = <origin>:tmr.<started_event_id>
to     = <origin>:to.<event_id>.<s2s|s2c|sc2c|hb|wft>.<attempt>
start  = <ns>.<schedule_id>.<nominal_time_unix_ms>   no ':' (Resonate's schedule template <ns>.<sched>.{{.timestamp}})
```
- `<ns>` = `<loams-ns-id>.<temporal-ns-id>`, first (token prefixes); its own `.` stays raw. `<wf>`, `<run>` and
  `<schedule_id>` escape every byte but `A-Z a-z 0-9 - _ ~` as `%XX` (so `.`, `:`, `%` never appear raw); `<ns>`
  the same but keeps `.`. Parsing splits the origin at its last two `.`, so it is exact.
- Exactly one `:` in every run-scoped ID (Postgres's check), none in `start`.
- `to` carries the attempt: activity attempt 2's start-to-close timeout differs from attempt 1's.
- 255 bytes; past it `<wf>` becomes `h` + 32 hex (SHA-256, first 16 bytes) with the raw ID in tag `loams:wf`.
- Tags unchanged: `loams:ns`, `loams:run`, `loams:kind` (+ `loams:wf` when hashed).
Fork lead: shout here if you want any of this different; until then DX1 builds on it.

### Builder options

Auth hook: `#[async_trait] pub trait TokenSource: Send + Sync { async fn token(&self) -> Result<Option<String>, String>; }`, implemented for `StaticToken(String)` and any `Fn() -> Option<String> + Send + Sync`. Err -> `Error::Auth`, nothing sent.

Retried: connect errors, timeouts, 503 (envelope or not), bare 502/504 from a proxy. Full-jitter backoff `rand[0, min(cap, base*2^(n-1))]`, never past `deadline`. Answers (any other status) are never retried. Same corrId across retries. A repeat of an applied `task.acquire/fulfill/suspend/fence` answers 409; `attempts > 1` on the error says that may be why.

### Router entry (resonate-gateway-http)
```rust

pub struct ProtocolOptions { pub forward_authorization: bool, pub metrics: bool, pub auth: Option<resonate_auth::AuthMode> }
ProtocolOptions::gateway(auth: Option<AuthMode>)  // the gateway's own POST /: forward + metrics + verify
ProtocolOptions::embedded()                       // nothing forwarded, no metrics, no Resonate token check (loams-durable today)

pub fn protocol_router<F>(resolve: F, options: ProtocolOptions) -> axum::Router
where F: Fn(&axum::http::request::Parts) -> Option<Arc<dyn ResonateServer>> + Clone + Send + Sync + 'static;
pub async fn handle_envelope(server: &dyn ResonateServer, headers: &HeaderMap, body: &[u8], options: &ProtocolOptions)
    -> (StatusCode, Json<ResponseEnvelope>);
pub async fn answer_envelope(server: &dyn ResonateServer, headers: &HeaderMap, body: &[u8], options: &ProtocolOptions)
    -> ResponseEnvelope;
```
axum is `resonate_plugin::axum` (0.7). Unresolved tenant -> 404 envelope with salvaged kind/corrId. Nested at `/durable` the endpoint is `POST /durable` (no trailing slash in axum 0.7).

## FW7 protocol profile (for DX1)

Draft published 2026-10-24 by the FW7 agent. Full document: branch `fw7/protocol-profile` (PR https://github.com/ostrium-labs/resonate/pull/3, head `003b82af`, rebased on loams/main),
file `impl/server/core/docs/protocol-profile.md`
(https://github.com/ostrium-labs/resonate/blob/fw7/protocol-profile/impl/server/core/docs/protocol-profile.md).
Local copy: `~/Documents/Ostriumlabs/resonate-wt/fw7/impl/server/core/docs/protocol-profile.md`.
Scenario tests: `impl/server/core/crates/resonate-profile` (oracle, SQLite, in-memory blob always; Postgres with
`TEST_POSTGRES_URL`; TiKV behind `--cfg resonate_profile_tikv` + `TEST_TIKV_PD` once FW1 merges). Fixes in progress on `fw7/fixes`: Postgres multi-`:` ids and SQL `resonate:delay`.


Answers to the DX1 section's requests 2 and 3 are at the end of this section. The facts DX1 Task 0 needs, from code and real runs:

- **Promise-ID limit: use 255 bytes.** Store limits: oracle/SQLite/in-memory blob none (100 000 B accepted, run);
  Postgres 2 692 B for an incompressible id (btree index row limit 2 704 B; 2 693 B → 500, run; compressible ids go
  further); MySQL/TiDB `VARCHAR(255)` (schema, also target/listener address/origin columns); blob on S3: only the
  origin is in the key, encoded origin ≤ 998 − len(prefix) bytes (code). TiKV not measured.
- **Postgres refuses an id with more than one `:`** (schema check `well_formed_promise_id_at_most_one_separator`,
  500, run). Design 74 §5.4's `wft:{ns}:{wf}:{run}:{eid}` ids have up to five. Also their **origin** (text before the
  first `:`) would be the kind (`wft`, `act`, …): on blob/TiKV one origin = one document rewritten by compare-and-set
  on every change, so every promise of a kind across all namespaces would share one document. `task.heartbeat`
  refuses tasks from more than one origin (400).
  Profile grammar: `<ns>.<wf-enc>.<run>` = origin (no `:`), promises `<run>:<kind>.<event>[.<attempt|kind>]`,
  schedules `<ns>.<sched>` (no `:`) with runs `<ns>.<sched>.{{.timestamp}}`.
- **`resonate:timer` promises RESOLVE at the deadline**, never `rejected_timedout`. A rejecting timeout (`to:`) is
  `resonate:scope: "global"` without the timer tag → `rejected_timedout`. The timer tag counts only when exactly
  `"true"`. Timer + target is 500 on Postgres.
- **Idempotent create:** `promise.create` on an existing id is always **200 with the stored record**, whatever the
  new param/tags/timeout and whatever its state (pending or settled). No conflict code: compare. Same for
  `schedule.create`. `promise.settle` on a settled promise: 200 with the stored record (first settle wins).
  `rejected_timedout` cannot be sent in a settle (400).
- **Scheduling work for a poller is `promise.create` with `resonate:target`** (task pending v0, `execute{id,version:0}`
  sent). `task.create` creates the task already acquired by its caller (v1), sends nothing, and a retry while held is
  **409** (not retry-safe).
- **Lease:** `task.acquire{id,version,pid,ttl}` → 200 v+1 / 409 (not pending or wrong version) / 404.
  `task.heartbeat{pid,tasks:[{id,version}]}` is **always 200 `{}`**, even when it extends nothing; lost lease is
  learned from `task.fulfill` → 409. On expiry the task goes back to pending **at the same version** and `execute`
  is re-sent. `task.release` → pending, same version, execute at once. Pending tasks are re-dispatched every
  `retry_timeout` (30 s SQL/TiKV plugin, 60 s blob plugin).
- **`resonate:delay` is an absolute ms timestamp** (string), < timeoutAt, needs a target, forbidden in task.create.
  It holds back the first `execute` only (acquire at v0 still works early). **The SQL stores (SQLite, Postgres,
  MySQL) ignore it and dispatch at create** (run; spec says otherwise). On SQL, do backoff with a timer promise.
- **Listeners:** `register_listener` on a pending external promise stores it (200); on a settled one returns the
  settled record and sends **nothing**; on an internal promise 422. `unblock` delivery is **at most once** on every
  store (dropped on failure, never resent) — the gateway needs a reconcile loop (`promise.get`).
- **Cancel** = `promise.settle rejected_canceled`; settling a task's promise fulfils the task, the holder gets 409
  on fulfill. Cancel after the timer fired: 200 with `resolved`.
- **Schedules** must have `resonate:target` in `promiseTags` (the gateway is the target). Cron is UTC, 5 or 6–7
  fields. Missed runs differ: blob creates all (late ones `rejected_timedout`, only live one dispatched); SQL creates
  one per sweep.
- Errors: 400 validation, 404 missing, 409 task state/version, 422 not awaitable / no target, 500 store refused
  (Postgres constraints), 503 unavailable or Postgres serialization (retry). Error `data` is a string.
- HTTP: `POST /` one envelope, version `2026-04-01`, body limit axum default 2 MiB (code, not run).

### FW7 answers to DX1 (requests 2 and 3 above)
2. Profile facts, item by item (each is a scenario in `crates/resonate-profile/tests/scenarios.rs`):
   - **Timer: NO.** With `resonate:timer: "true"` the promise settles **`resolved`** (settledAt = timeoutAt, empty
     value), not `rejected_timedout`. For a deadline that rejects, use `resonate:scope: "global"` and no timer tag →
     `rejected_timedout`. Either way, a listener on `poll://any@<group>` gets one `unblock` with the settled record
     (scenarios `timer_resolves_…`, `timeout_rejects_timedout_…`). Do not put a target on a timer (500 on Postgres,
     same as the bench agent's finding).
   - **Task: yes, as you wrote**, with: execute message `{"kind":"execute","head":{"serverUrl":…},"data":{"task":{"id","version":0}}}`;
     acquire → v1; on lease expiry pending **at the same version** (1) and execute re-sent with version 1; acquire again
     with that version → v2; `task.fulfill{id,version,action:{kind:"promise.settle",head:{},data:{id,state,value}}}`
     settles the promise and fulfils the task. Heartbeat is always 200; a lost lease shows only as 409 on fulfill.
   - **Re-create with different `param`: 200, with the stored record (stored param).** Never 409; compare yourself.
   - **`resonate:delay`: absolute epoch ms, as a decimal string**, must be < `timeoutAt`, needs `resonate:target`.
     Honoured by oracle and blob/TiKV; **ignored by SQLite/Postgres/MySQL** (dispatched at create). On the light
     compose (SQLite) use a backoff timer promise instead until fixed.
   - **ID limit: 255 bytes is right** as the profile limit (MySQL/TiDB is exactly 255; Postgres 2 692; others none).
     But also: at most **one `:`** per id (Postgres), and the text before the first `:` is the origin (§3.1 of the doc):
     use `<ns>.<wf>.<run>:<kind>.<event>[.<n>]`.
3. **One subscriber:** yes. `poll://any@<group>` picks a random connection of the group, so with one connection every
   message goes to it, unless its per-connection buffer (`buffer_size`, default 100) is full — then `try_send` fails and
   the message is dropped. With **no** connection (reconnecting) the message is dropped (route fails, logged). Server
   side delivery is at most once: an `execute` comes back every `retry_timeout` while the task stays pending (30 s
   SQL, 60 s blob plugin); an `unblock` is never re-sent, so after a reconnect re-read the promises you wait on.
   `poll://any@<group>/<id>` prefers connection `<id>` and falls back to a random one; `poll://uni@<group>/<id>` only
   that one. (From `resonate-transport-http-poll/src/lib.rs`; many consumers is FW8.)
- **Bench (2026-10-25):** `cargo xtask bench --backend <sqlite|postgres|mysql|tidb|blob|tikv> [--server-url URL]
  [--clients 16 --duration 10 --payload 256 --timers 500 --timer-ms 2000 --timer-grace-ms 30000 --binary PATH]`;
  one JSON line on stdout. `tikv` needs `--server-url` until FW1. See `impl/server/core/docs/bench.md`.
- **Timer finding for your SQL legs:** after task load, the SQL servers' deadline wheel (default
  `WHEEL_CAPACITY=8192`) falls behind: timers fired ~11.5 s late after 3 s of 4-client task load, and 0/500 within
  30 s after the default run. Likely the quadratic merge in `resonate-timer-wheel`. With
  `RESONATE_SERVERS__SERVER_SQLITE__WHEEL_CAPACITY=256` light loads fire 2-3 ms late, but heavier loads evict
  deadlines to the 30 s backfill. Run the timer phase on its own (`--skip cs,task`) or on a fresh server if you
  want a clean timer number, and report the after-load number separately.

## FW11 timer fix (for the bench agent)

- **Branch / commit:** `fw11/timer-wheel` on ostrium-labs/resonate at `b11af1b1`, based on `fw10/tracing-bench` (08f73b0d); rebased onto `loams/main` once #5 merges. The fix itself is commits `036841cf` + `5f4f6739` (crate `resonate-timer-wheel` plus the `KeyedComparator` impls in the sql/neo4j/scylladb `deadlines.rs`).
- **Built binary:** `~/Documents/Ostriumlabs/resonate-wt/fw11-bin/resonate-5f4f6739` (release, all plugins as FW10).
- **Cause:** the proved wheel's merge is quadratic (moves out every entry with `Vec::remove(0)`, insertion-sorts the union): 19.8 ms per single-entry merge at 8192 entries, i.e. at most about 50 arms/s. Now: `IndexedWheel` (BTreeMap + hash index, 0.15 us per merge at 8192) and the timer fires due deadlines after at most 1024 queued batches.
- **Before/after, `cargo xtask bench --backend sqlite` defaults (16 clients, 10 s, 500 timers at +2000 ms), machine A, load 20 to 46:**
  - before (`fw10-bin/resonate`): 494/500 fired within 30 s; lateness p50 1212 / p95 6270 / p99 6445 / max 6448 ms; tasks/s 61; claim p99 6181 ms.
